# KnowledgeOS Correctness + Lean Orchestration Spec v1

Spec ID: SPEC-20260915-001
Status: accepted; implementation candidate under validation
Date: 2026-09-15
Scope: two sequential implementation stages, model-neutral safety, GPT-5-family compatibility

## 0. 产品目标与范围

本规范将已经确认的方向细化为两个可独立验收的实现阶段：先修正确性，再减少重复调度。它不是 Astra 专属模块，也不是重新设计 OS。

产品不变量：small kernel、pluggable modules、optional apps、project-level strictness，以及用户可见的真实运行汇报。安全与证据规则由确定性逻辑执行，模型只在允许范围内选择实现路径。

本规范已获接受，作为候选版本的验收合同。实现与验证状态以 CHANGELOG.md 和 docs/LIVE-REPORT.md 为准，不能从规范文字推断功能已通过。GPT-5 系列是兼容目标，不是已通过测试的型号集合。实施应先冻结准确的代码、模板和模型/宿主基线，再据本规范建立失败测试。

MUST 表示强制验收条件，SHOULD 表示优先方案；接口字段是拟议合同，不应作为当前 CLI 已支持的参数使用。

### 范围限制

- 不新增大型调度器，不重写 Workbench，不增加与 complete-task 重复的 finalize 命令。
- 不取消六阶段语义、真实产物检查或 SYNC_OK 证据要求。
- 不通过更换模型、提示模式或缓存降低项目门禁。
- 不记录隐藏思维链；仅保存公开摘要、权限依据和命令/产物证据。
- 不编辑历史 ledger、旧 Spec、既有自定义规则，不自动激活新 Spec 覆盖其他工作。
- 不在本轮修改全局 Prompt、实现源码或发布 GitHub。

## 3. 第一步 SPEC-A：正确性修复

### A1. 任务/聊天级 Spec 绑定

目标：每个 run 使用与任务相关且可追溯的 Spec；不再被项目最近 active Spec 或另一聊天的状态串线。

- MUST 支持任务显式绑定一个 Spec，以及显式声明本任务不适用 Spec；未指定与不适用是不同状态。
- SHOULD 优先复用并扩展 align-spec、context-pack 的现有入口。align-spec 成功后，后续 context-pack MUST 实际使用该绑定。
- 首次解析顺序：任务显式绑定或不适用声明 > 明确关联的聊天 Spec > 尚未确认的项目候选。项目 active_spec 仅是候选，不可默默变成任务合同。
- 无真实聊天 ID 时必须使用显式 thread_id 或仅保留任务绑定；不得依赖项目级 current.json 猜测属于哪个聊天。
- 同层来源冲突、Spec 不存在、路径越界或内容不完整时返回明确诊断，不自动挑选“最新”版本。
- 已撤销或跨项目的绑定不得静默回退；显式绑定优先级仅用于选择上下文，不能覆盖聊天或项目更严格的范围约束。约束互相矛盾时阻断并解释。
- run 创建后冻结绑定来源、Spec ID、内容指纹及任务/聊天引用。其他任务变更项目 active_spec 不使此 run 无故漂移。
- 已绑定 Spec 本身变化时，受影响操作前和完成时都必须发现漂移。允许显式重新对齐并追加新快照/事件，不覆盖旧快照，随后更新相关计划和验证。
- 若项目明确要求 Spec，而任务未绑定或声明不适用不被该策略允许，应阻断；普通无 Spec 任务可以在政策允许时明确记录 none。

最小可观察结果：`spec_id`、`binding_source`、`spec_fingerprint`、`binding_status`。复用 task/run/context 数据，不建立新的 Spec 数据库。

### A2. 真实宿主能力识别

目标：避免再次推荐没有运行入口的 Maestro，或将角色说明当成已安装的 subagent 类型。

- MUST 区分 registered、adapter_resolvable、host_available、execution_verified；后两者缺证据时为 unknown，不得从注册表推断为 true。
- host_available 必须关联当前宿主/会话工具清单与 schema 版本。没有宿主快照时只输出待确认候选，不列为已确认可调用。
- generic spawn 不支持 agent_type 时只能使用其真实 schema，再通过提示分配角色；不得传入虚构参数或宣称验证了原生角色类型。
- execution_verified 必须关联本次或明确标注范围的历史调用 ID、终态和输出证据；历史成功不证明本会话可用。
- bare Maestro 不作为默认 required stage；没有适配器或运行入口时不持续推荐。保留历史记录和用户自定义项，不做破坏性删除。
- 计划缓存必须绑定宿主能力指纹，断连、重启或 schema 变化后失效。
- 派遣数按 invocation_id 去重，running/completed 两条事件不是两个 agent；失败、超时、取消、晚到恢复与跳过分别显示。
- 能力统计准确区分内置网页检索与外部 MCP；扩展分类应向后兼容旧记录，不将不存在的运行时伪装成 MCP。

这层由宿主桥接提供事实，CLI 负责解析与验证；不让 shell 冒充拥有宿主内部 spawn 能力。

### A3. 授权一致性

目标：已授权的有界操作继续执行，真正越界的操作仍然询问或阻断。

- MUST 输出一致的 `approval_required`、`approval_reason`、`authorization_source`；过渡期旧字段由同一结果派生，不得一边允许一边无条件 ask-first。
- 既有授权必须有可核查来源，绑定项目/任务范围、操作类别、目标、数量/成本限制、期限或撤销条件，不能由 Agent 自称“用户已经同意”。
- 默认有界只读 subagent 不递归、不扩大访问；重叠写入、范围外改动、敏感访问、破坏性或外部/付费操作按相应授权和项目政策处理。
- 本版将“最多三个”解释为单个父任务累计最多三个独立子代理调用，而非通过关闭代理无限续用的并发额度；同一幂等调用重试不重复计数，新替代调用消耗新额度。第四个需扩展授权，宿主更低限制始终有效。
- 项目明确的逐任务确认门禁仍有效；更高层宿主或工具安全约束优先。
- 权限变更或授权撤销后，旧 dispatch 不得继续授权新副作用。每个有副作用动作仍通过当前适用边界检查。
- 无工具权限属于能力缺口，不得错误地要求用户“授权一个不存在的工具”。

### A4. 验收场景

| 用例 | 输入/故障注入 | 必须结果 |
| --- | --- | --- |
| A-T01 | 先将 T1 对齐 S1，项目 active 为无关 S2，再 context-pack | 采用 S1，明确来源；原缺陷测试修前失败、修后通过 |
| A-T02 | 同项目两个聊天绑定不同 Spec，切换 current 与 active 指针 | 两个 run 不串线；不覆写旧快照 |
| A-T03 | Spec 不存在、同层冲突、显式 none 与项目要求冲突 | 准确阻断；普通允许 none 的任务正常运行 |
| A-T04 | 已绑定 Spec 修改；仅无关 Spec 修改 | 前者发现漂移并要求重新对齐；后者不误报 |
| A-T05 | registry 声明工具，但宿主无工具/断连/schema 改变 | 不报告 host_available；缓存失效；失败公开 |
| A-T06 | generic spawn、running 后 completed、超时后晚到结果 | 参数有效，调用计数唯一，状态与恢复证据准确 |
| A-T07 | 有界预授权 vs 过期/撤销/更换目标/逐任务 gate | 前者不重复询问；后者不能沿用原授权 |
| A-T08 | 旧 Maestro 配置及项目自定义 registry | 不强制不可用编排器；保留自定义与历史数据 |

阶段出口：A-T01 至 A-T08、既有受影响测试及 guardrail scenarios 全部通过；新初始化项目与旧项目副本完成 dry-run。不得进入全局推广后才补正确性验证。

## 4. 第二步 SPEC-B：精简调度但保留全部保障

前置条件：SPEC-A 验收通过。不能用更短提示绕过尚未修好的绑定或权限问题。

### B1. 单一权威规则源

- MUST 有一份版本化通用合同，复用现有模板/生成器；全局、项目启动提示与 agent-guide 从它派生，不各自维护一份流程全文。
- 生效规则包只包含适用不变量、当前任务/相关 Spec/Plan、有效权限、启用检查及参考索引；历史资料按需读取。
- 项目自定义限制只按已定义的配置优先级合并；来源冲突必须显示，不可静默覆盖。
- 保留用户指定语气、范围保护、显式汇报以及所有安全不变量。生成器更新不重写用户自定义段落。
- 输出合同版本与配置指纹以定位旧项目漂移，不能把所有历史记录装进启动上下文。

### B2. 完成检查收敛

- 正常路径由 eval-task 生成真实验收记录，再由现有 complete-task 执行最终 lifecycle/context/effects/decisions/dispatch/sync 检查。
- 独立 verify-* 和 dispatch-report 保留给诊断、人工审计及旧客户端；正常提示不再要求先逐个调用一遍同样检查。
- eval/产物与被验证输入的指纹 MUST 对齐。eval 后相关产物或策略变化，最终完成须拒绝过期证据或触发相应重新验证，不能只认文件含 passed。
- repeated complete 不得重复同步或重复外部副作用；以 run 和相关输入指纹识别重复操作。失败重试必须恢复原尝试或显式新尝试，不能掩盖部分完成。
- 模块的 warn/enforce/off 仍由项目策略控制，兼容提示不改变 strictness；全部失败、警告及 pending 都准确显示。

### B3. dispatch 复用

- 复用现有预检结果，将计划与 run 原子绑定，避免 run 前后由模型发起两次相同解析。
- 指纹至少覆盖任务范围、Spec 绑定、相关路由/权限/授权策略、宿主 schema；相关变更必须失效重算。
- 只减少重复规划，不缓存永久写权限；重新校验发现变化必须在副作用发生前阻断或生成新计划。
- 旧的重复 dispatch 调用仍被接受，明确返回 reused/recomputed 及原因，不生成虚构的新派遣。

### B4. 显式 Checkpoint 的低成本实现

- 保留 route/plan/review/dispatch/execute/report 六阶段语义；不得为了省调用将六阶段改为全自动通过。
- route/plan/dispatch 等真实成功命令可发出对应阶段事件。review/execute 必须关联实际审阅、运行或产物证据，不可用“计划要做”替代“已经做了”。
- 自动事件记录 producer、task/run、输入指纹、证据引用与幂等 ID。验证器接受受支持命令产生的事件和旧 phase-task 事件；不能仅因一行 JSON 自称 producer 就通过。
- 统一产生短人类摘要和机器标记。宿主可渲染时展示关键阶段；CLI-only 宿主保留明确回显规则。不得宣称 CLI 打印就证明用户已看到。
- 保留 KOS_DECISION、必要 CHECKPOINT_OK、完整能力汇总、最终真实 SYNC_OK；不要求用户每阶段点击确认。未调用能力、失败、跳过原因可折叠但可查询，不隐藏必要警告。

### B5. 验收场景

| 用例 | 输入/故障注入 | 必须结果 |
| --- | --- | --- |
| B-T01 | 全局、模板、旧项目有不同版本及用户自定义段 | 生成一致合同；保留自定义；冲突有来源 |
| B-T02 | 缺 eval/产物/阶段，伪造事件或工具返回 stub | 单次 complete 仍不能虚假成功；检验真实内容 |
| B-T03 | eval 后改产物，预检后改写策略或宿主工具 | 过期证据和计划失效；无检查后越界窗口 |
| B-T04 | 重复 complete、同步中断后重试、重复 dispatch | 不重复外部副作用；复用或重算可解释 |
| B-T05 | 六阶段自动/旧手动事件混合、重试重复发事件 | 阶段计数准确；未发生的工作不能自动通过 |
| B-T06 | 用户可见层缺失、CLI-only 与宿主 UI | 明确显示能力边界；必要状态与原因可读 |
| B-T07 | 原命令、旧 ledger、新旧模板、项目严格度组合 | 兼容已支持接口；旧历史不改写；策略不降级 |

阶段出口：上述场景和完整回归通过；相同真实任务下重复调度减少，且产物质量、失败披露、权限保护不退化。

## 5. GPT-5 系列推广合同

### 一套检查，两种提示深度

SHOULD 在现有项目配置中增加单一可选 `guidance_mode: compact | guided`，而不是多套模型专属 OS。

- compact：提供目标、边界、完成条件和必要入口；减少重复步骤描述。
- guided：从同一合同派生简短的顺序提示和参数示例，适用于需要更多引导的模型或团队。
- 两种模式 MUST 使用相同规则版本、命令语义、验证器、事件格式及安全门禁。guided 不代表更严格，compact 不代表放开权限。
- 未验证模型默认 guided 或保留现有可工作的指导方式；不得仅凭名称 GPT-5/GPT-6 自动降级或宣称兼容。
- 模型身份/可用性由宿主明确提供；不能通过新增 Prompt 假造模型或工具能力。

### 测试矩阵与发布条件

目标优先顺序：当前可用的 Astra、GPT-5.6 Sol、GPT-5.6 Luna、GPT-5.5。更早 GPT-5/GPT-5.1/GPT-5.2 仅在实际运行接口和版本可用时加入；不可用即标注 untested，不用较新型号成绩替代。

MUST 对每个准备宣称支持的准确 model id/版本/思考设置/宿主版本分别保存 current、guided、compact 结果。所有型号当前状态均为待验证；本轮子代理规范审阅不算 GPT-5 运行测试。

首轮筛选采用 6 类固定任务，每类至少 3 次独立运行：简单说明/文档改动、稳定复现的代码缺陷、科研模型审阅、双聊天 Spec、工具缺失/stub、敏感或外部操作阻断。固定代码与权限，任务顺序交叉，保留输入和原始结果。使用临时项目与隔离 fixtures，不测试真实破坏性操作。

进入某型号试点的最低门槛：

1. 全部确定性负例通过；观测到任何越权、串 Spec、伪造完成或隐藏失败均不得发布。
2. 每个必需任务场景至少有可独立验收的成功结果；不以总平均掩盖某场景完全失败。
3. 新指导方式的独立验收成功率不低于该型号基线，失败经归因无新增严重退化；不声称小样本证明普遍等效。
4. 记录重复调用数、人工中断、耗时分布、可获得的真实 token 和结果质量；减少日志文本不是单独成功指标。
5. compact 若退化则在该型号保留 guided，不回退第一步正确性修复、不关闭 gate。

先在两个不同项目类型试点并记录版本，再推广该已通过型号。准确支持列表必须附证据与测试日期，禁止笼统写“全部 GPT-5 已支持”。

## 6. 迁移、回滚与交付

- 每步先复现，再最小修复，再临时项目 dry-run，再旧项目副本与新项目 smoke；最后完整回归。doctor 通过不替代行为测试。
- harness-audit 迁移先给 diff/备份与版本要求，默认不覆写 custom registry、旧 Spec 或历史 evidence；不适用的新字段采取明确兼容行为。
- 迁移必须有幂等步骤与中断恢复记录，半途失败后的重试不重复覆盖；未知的安全关键字段不可被旧客户端静默忽略，应明确拒绝执行。
- 历史 run 保持原验证/读取语义与原记录，迁移后新 run 使用新绑定规则。无法安全解释的老活动 run 明确暂停对齐，不替它补造证据。
- 配置回滚只还原本次配置变更，保留期间新增 ledger；先检查版本兼容再回滚二进制。无法读取新记录的旧版不能静默接管。
- 第二步提示回滚可独立执行；已修复的 Spec 隔离、能力真实性和授权保护不得为减少摩擦被移除。
- 发布内容只包含审阅后的代码、模板、测试、Spec、CHANGELOG/LIVE-REPORT。排除本地绝对路径、凭据、研究数据与本轮私有运行记录。
- GitHub plugin 读取不等于授权推送；Spec 起草轮不创建远端提交/PR。本实施轮依据用户的版本更新请求发布候选分支，发布时必须报告准确分支、commit、测试范围与兼容列表，不自动升级为 main 合并或稳定版本认证。

## 7. 最终完成定义

这项产品修改只有在 SPEC-A、SPEC-B 均满足验收，迁移/回滚通过，并至少一个明确 GPT-5 型号完成实测后，才能宣称“已实现并可向该型号推广”。

仅完成本规范、单次模型回答、adapter 解析或 doctor 通过，均不能代替实现与跨模型验收。
